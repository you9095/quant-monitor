## 三、我的具体反省

### 反省1：阻塞性问题必须立即派发，不是"等有空了再说"

pandas缺失是阻塞性问题——没有pandas，策略脚本根本无法启动，整个daily_run链路都断了。

**我把它当成了"可以稍后处理"的小问题，但实际上这是P0级别的阻塞性问题。**

**正确的做法应该是：**
- 发现阻塞性问题（pandas缺失、脚本被删除、cron全部失败）立即标记为P0
- 24小时内派发给对应角色（运营）
- 要求24小时内修复
- 每4小时跟踪一次进度
- 修复后验证整个链路恢复正常

### 反省2：影响数据真实性的任务必须经过审核，不能"谁做谁负责"

重建daily_full_chain.sh是一个影响数据真实性的任务。主Agent独立完成，使用了模拟模式，没有经过任何审核。

**这是任务管理的严重缺失。** 影响数据真实性的任务必须经过审核，不能"谁做谁负责"。

**正确的做法应该是：**
- 影响数据真实性的任务（重建脚本、修改数据、切换模式）必须经过审核
- 审核流程：规划者审核方案 → 测试审核测试用例 → 运营审核环境 → 最终上线
- 任务描述中必须明确："禁止使用模拟数据，必须使用真实市场数据"
- 上线后必须验证数据正确性（用已知正确值验证）

### 反省3：连续失败必须升级，不能"再试一次"

9月1日-9月9日，连续多次修复失败，每次都是主Agent独立尝试，每次都自报"成功"但实际没修好。

**我没有设置"连续失败必须升级"的规则。** 连续2次失败就应该升级：换思路、换角色、深入调查根因，而不是"再试一次"。

**正确的做法应该是：**
- 第1次失败 → 分析失败原因，调整方案
- 第2次失败 → 升级处理，组建跨角色团队，深入调查根因
- 第3次失败 → 暂停修复，先做完整的根因分析，制定详细的修复计划，经审核后再执行
- 禁止"在没有新信息的情况下重复同样的修复方案"

### 反省4：任务描述必须包含约束条件，不能只说"做什么"

我给主Agent派发的任务是"重建daily_full_chain.sh"，但没有包含约束条件：
- 禁止使用模拟数据
- 必须使用真实市场数据
- 必须先排查策略脚本缺失的原因
- 必须确认pandas可用
- 必须备份已有数据
- 必须验证数据正确性

**任务描述只说了"做什么"，没有说"不能做什么"和"必须满足什么条件"。** 这导致主Agent按照自己的理解执行，使用了模拟模式。

**正确的做法应该是：**
- 任务描述必须包含：做什么、不能做什么、必须满足什么条件、验证标准是什么
- 特别是影响数据真实性的任务，必须明确："禁止使用模拟数据，必须使用真实市场数据，累计盈亏不可覆盖"

## 四、我的改进措施

### 4.1 任务派发SOP

#### SOP-01：阻塞性问题处理

```
发现阻塞性问题（pandas缺失、脚本被删除、cron全部失败等）：
  1. 立即标记为P0优先级
  2. 24小时内派发给对应角色
  3. 要求24小时内修复
  4. 每4小时跟踪一次进度
  5. 修复后验证整个链路恢复正常
  6. 记录事故原因和处理过程
```

#### SOP-02：影响数据真实性的任务审核

```
影响数据真实性的任务（重建脚本、修改数据、切换模式等）：
  1. 任务描述必须包含约束条件：
     - 禁止使用模拟数据
     - 必须使用真实市场数据
     - 累计盈亏不可覆盖
     - 修改前必须备份
  2. 执行前必须经过规划者审核方案
  3. 执行后必须经过测试者验证数据正确性
  4. 验证标准：用已知正确值验证（追电=27030.7等）
  5. 未通过审核和验证的任务不得上线
```

#### SOP-03：连续失败升级

```
修复任务连续失败：
  第1次失败 → 分析失败原因，调整方案
  第2次失败 → 升级处理，组建跨角色团队，深入调查根因
  第3次失败 → 暂停修复，先做完整的根因分析，制定详细修复计划，经审核后再执行
  禁止：在没有新信息的情况下重复同样的修复方案
```

### 4.2 任务模板

#### 模板：数据修复任务

```
任务标题：[P0] 修复XX策略数据异常
任务描述：
  - 问题：XX策略累计盈亏异常（从X变成Y）
  - 目标：恢复正确数据，确保数据真实性
  - 约束条件：
    1. 禁止使用模拟数据，必须使用真实市场数据
    2. 累计盈亏不可覆盖，必须从历史正确数据恢复
    3. 修改前必须备份当前状态
    4. 禁止只改前端字段，必须追溯到数据源
  - 执行步骤：
    1. 根因分析：查看daily_chain.log，对比历史信号文件，找到数据异常的根本原因
    2. 制定修复方案：从哪个日期的正确数据恢复？如何恢复？
    3. 备份当前状态
    4. 执行修复
    5. 验证：用已知正确值验证（追电=27030.7，r32=3080.31等）
    6. 浏览器实测验证
  - 验证标准：
    1. 全部策略累计盈亏在正确基准±5%范围内
    2. 收益率格式为百分比
    3. live_days > 10
    4. 前端显示与API返回一致
  - 负责人：主Agent + 测试 + 运营
  - 截止时间：24小时内
```

### 4.3 优先级定义

```
P0（阻塞性/数据真实性）：
  - pandas等基础依赖缺失
  - 关键脚本被删除
  - cron全部失败
  - 累计盈亏异常突变
  - 数据被覆盖/数据投毒
  处理：立即处理，24小时内修复，每4小时跟踪进度

P1（重要功能）：
  - 单个策略运行失败
  - 单个API接口异常
  - 前端显示问题
  处理：48小时内修复，每天跟踪进度

P2（一般优化）：
  - 性能优化
  - 代码重构
  - 文档完善
  处理：本周内处理
```

## 五、总结

**我犯的最大错误是"只派发任务，不管理任务"。我派发了"重建daily_full_chain.sh"的任务，但没有包含约束条件，没有要求审核，没有跟踪进度，没有验证结果。**

**pandas缺失28天、脚本删除28天、修复失败10天——这些问题本应该在第一天就被升级处理，但因为任务管理缺失，持续了几十天。**

**未来我必须记住：派发任务只是开始，不是结束。必须包含约束条件、必须审核方案、必须跟踪进度、必须验证结果。连续失败必须升级，不能"再试一次"。**
