# 规划者角色反省报告 — 2026-08-31 数据灾难事故

> **角色**: 规划者 / 架构师
> **事故**: 2026-08-31 模拟模式数据覆盖事故
> **反省日期**: 2026-09-11
> **责任等级**: 架构设计责任（系统设计缺陷导致事故容易发生、难以发现）

## 一、我在系统设计中埋下了哪些隐患

### 1.1 "每日覆盖"模式的设计缺陷

**我设计了什么：**
- 每天生成一个新的 `{strategy}_{date}.json` 信号文件
- 新文件中的 `live_total_pnl` 是**重新计算**的，不是从昨天的文件累加

**这个设计的隐患：**
- 任何一天的计算错误都会"重置"整个历史
- 8月31日的模拟数据不是"新增了一天的错误数据"，而是"把之前50天的正确累计全部覆盖成了2天的模拟值"
- 没有"今日累计 = 昨日累计 + 今日盈亏"的保护机制

**正确的设计应该是：**
```
今日累计盈亏 = 昨日信号文件中的累计盈亏 + 今日盈亏
昨日累计盈亏必须从昨日的信号文件读取，不能重新计算
```

### 1.2 缺乏"数据不可变"的架构保护

**我设计了什么：**
- 信号文件可以被任何脚本随时覆盖
- work_logs可以被任何脚本随时覆盖
- 没有"累计字段不可修改"的保护
- 没有"修改前必须备份"的强制机制

**这个设计的隐患：**
- 模拟模式可以轻易覆盖正确的累计数据
- 没有任何机制阻止"数据投毒"
- 数据被覆盖后，如果没有备份，就无法恢复

**正确的设计应该是：**
- 累计字段（live_total_pnl、live_total_return、live_days）标记为"不可变"
- 修改这些字段前必须备份
- 修改这些字段必须有用户明确许可
- 建立"数据审计日志"，记录每次修改的时间、操作人、修改前后的值

### 1.3 缺乏"数据血缘追踪"

**我设计了什么：**
- 数据从work_logs → 桥接脚本 → 信号文件 → 后端API → 前端展示
- 但没有完整的血缘记录：每个数字从哪里来、经过了哪些转换、最终显示在哪里

**这个设计的隐患：**
- 数据出错时，无法快速追溯是哪个环节出了问题
- 9月修复时，花了10天才找到"数据源被模拟数据覆盖"这个根本原因
- 如果有血缘追踪，第一天就能发现问题

**正确的设计应该是：**
- 每个数字都有"数据来源"标记（data_source字段）
- 每次转换都记录在"数据血缘日志"中
- 前端显示时，可以追溯这个数字的完整来源链路

### 1.4 "模拟模式"作为降级方案的设计错误

**我设计了什么（或者说，我没有禁止什么）：**
- 当策略脚本缺失时，允许"降级"到模拟模式
- 模拟模式用随机数生成假数据
- 假数据和真数据用同样的格式存储，下游无法区分

**这个设计的隐患：**
- 在通用软件工程中，"优雅降级"是常见模式
- 但在金融数据场景下，"降级到假数据"不是优雅降级，是"数据投毒"
- 假数据比没数据危险100倍——没数据是透明的，假数据是隐蔽的

**正确的设计应该是：**
- **禁止模拟模式**，本项目只有"真实市场数据模拟交易"一种模式
- 策略脚本缺失时，正确的处理是：报错停止 / 用缓存 / 保持上日数据
- **绝不生成假数据**

### 1.5 缺乏"异常突变检测"机制

**我设计了什么：**
- 没有数据异常突变检测机制
- 累计盈亏从+27030变成-22（1000倍变化），系统没有任何告警

**这个设计的隐患：**
- 数据异常无法被及时发现
- 用户9月1日才发现数据不对，而事故发生在8月31日
- 如果有异常检测，事故发生当天就能发现

**正确的设计应该是：**
- 每天检查累计盈亏的变化幅度
- 单日变化超过±50% → 告警
- 方向反转（正变负/负变正）→ 告警
- 市值接近本金（±1%以内）→ 告警
- live_days < 10 → 告警

## 三、我的具体反省

### 反省1：在金融数据系统中，"数据不可变"应该是架构的第一原则

我之前的架构设计思路是："数据可以被更新，因为每天都有新的盈亏。"

**这个思路在金融数据系统中是错误的。** 累计盈亏不是"可以被更新的字段"，而是"不可变的历史账本"。今天可以新增一笔盈亏，但不能修改昨天的累计。

**正确的架构原则应该是：**
- 历史数据不可变（append-only）
- 今日累计 = 昨日累计 + 今日盈亏
- 昨日累计必须从昨日的文件读取，不能重新计算
- 修改历史数据必须有审计记录和用户许可

### 反省2："优雅降级"在金融数据场景下是危险的

我之前觉得"模拟模式"是一个合理的降级方案——主功能不可用时，用备用方案填补，至少系统还在跑。

**这是通用软件工程的思路，不是金融数据系统的思路。** 在金融数据场景下，"降级到假数据"不是优雅降级，是"数据投毒"。

**正确的降级方案应该是：**
- 策略脚本缺失 → 报错停止，通知用户
- 数据获取失败 → 用缓存，保持上日数据
- 计算失败 → 不更新，保持上日数据
- **绝不生成假数据**

### 反省3：数据血缘追踪不是"锦上添花"，是"必需品"

我之前觉得数据血缘追踪是"高级功能"，可以以后再加。

**这次事故证明，数据血缘追踪是必需品。** 如果有完整的血缘追踪，9月1日就能发现"这个数字来自8月31日的模拟模式"，而不是花了10天才找到根本原因。

**正确的架构应该包含：**
- 每个数字都有data_source标记
- 每次转换都记录在血缘日志中
- 前端可以追溯数字的完整来源链路

### 反省4：异常检测应该内置在系统中，不是"靠人发现"

我之前觉得"数据异常了用户会发现"。

**这是错误的。** 用户不可能24小时盯着数据，而且异常可能发生在周末或节假日。异常检测应该内置在系统中，自动运行、自动告警。

**正确的架构应该包含：**
- 每日自动检查数据异常突变
- 异常时自动告警（通知到具体的人）
- 严重异常时自动停止后续操作

## 四、我的改进措施

### 4.1 架构改进清单

#### ARCH-001：累计数据不可变机制

```
设计原则：
  1. live_total_pnl / live_total_return / live_days 标记为"不可变字段"
  2. 今日累计 = 昨日累计 + 今日盈亏
  3. 昨日累计必须从昨日的信号文件读取
  4. 修改不可变字段前必须备份
  5. 修改不可变字段必须有用户明确许可
  6. 建立"数据审计日志"，记录每次修改
```

#### ARCH-002：数据血缘追踪

```
设计原则：
  1. 每个信号文件必须有 data_source 字段
  2. data_source 必须包含：数据来源、生成时间、生成脚本
  3. 禁止 data_source 包含 "simulated" / "模拟"
  4. 建立"数据血缘日志"，记录每次转换
  5. 前端可以追溯数字的完整来源链路
```

#### ARCH-003：异常突变检测

```
设计原则：
  1. 每天收盘后自动检查数据异常
  2. 检测规则：
     - 累计盈亏单日变化超过±50% → 告警
     - 方向反转（正变负/负变正）→ 告警
     - 市值接近本金（±1%以内）→ 告警
     - live_days < 10 → 告警
     - data_source 包含 "simulated" → 立即停止
  3. 告警必须通知到具体的人
  4. 严重异常时自动停止后续操作
```

#### ARCH-004：统一Python环境

```
设计原则：
  1. 所有脚本统一使用 /usr/local/bin/python3（Homebrew Python 3.14）
  2. 建立 requirements.txt，锁定所有依赖版本
  3. 每天检查基础依赖是否可用
  4. 策略脚本和后端服务使用同一个Python环境
```

## 五、总结

**我犯的最大错误是用"通用软件工程"的思路设计"金融数据系统"。通用软件工程中的"优雅降级""每日覆盖""字段可更新"等模式，在金融数据场景下都是危险的。**

**金融数据系统的第一原则应该是：数据不可变。第二原则：绝不生成假数据。第三原则：异常必须自动检测和告警。**

**未来我设计任何金融数据系统时，必须先问自己：这个设计会不会导致历史数据被覆盖？会不会导致假数据被当成真数据？会不会导致异常无法被及时发现？**
