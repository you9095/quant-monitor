# 数据部角色反省报告 — 2026-08-31 数据灾难事故

> **角色**: 数据部 / 数据工程
> **事故**: 2026-08-31 模拟模式数据覆盖事故
> **反省日期**: 2026-09-11
> **责任等级**: 数据治理责任（数据质量监控缺失、数据血缘缺失、数据标准缺失）

---

## 一、我在数据治理中犯了哪些错误

### 1.1 数据质量监控缺失

**我应该做但没做的：**
- ❌ 没有建立数据质量监控体系
- ❌ 没有监控累计盈亏的异常突变（从+27030变成-22，1000倍变化）
- ❌ 没有监控数据格式的一致性（收益率从百分比变成小数）
- ❌ 没有监控数据来源的合法性（data_source从"真实daily run"变成"simulated_work_log"）
- ❌ 没有监控数据完整性（live_days从50天变成2天）
- ❌ 没有设置数据质量告警规则

**实际情况：** 8月31日模拟数据覆盖正确数据后，数据部没有任何告警，没有任何发现。用户9月1日才发现数据异常。

### 1.2 数据血缘追踪缺失

**我应该做但没做的：**
- ❌ 没有建立数据血缘追踪体系
- ❌ 没有记录每个数字的完整来源链路（work_logs → 桥接 → 信号文件 → API → 前端）
- ❌ 没有记录每次数据转换的时间、操作人、转换规则
- ❌ 没有在前端提供"数据来源追溯"功能

**实际情况：** 9月修复时，花了10天才找到"数据源被模拟数据覆盖"这个根本原因。如果有数据血缘追踪，第一天就能发现问题。

### 1.3 数据标准缺失

**我应该做但没做的：**
- ❌ 没有建立数据标准文档（每个字段的定义、格式、单位、取值范围）
- ❌ 没有明确规定收益率必须用百分比格式（不能用小数）
- ❌ 没有明确规定累计盈亏必须是"逐日累加"（不能"重新计算"）
- ❌ 没有明确规定data_source不能包含"simulated"
- ❌ 没有建立数据schema校验机制（每次写入信号文件前校验格式是否符合标准）

**实际情况：** 8月31日模拟数据把收益率写成了小数形式（-0.002243），累计盈亏"重新计算"成了2天的值，data_source标记为"simulated_work_log"——这些都违反了数据标准，但因为没有标准和校验，所以没有被发现。

### 1.4 数据备份与恢复机制缺失

**我应该做但没做的：**
- ❌ 没有建立数据自动备份机制（每天备份信号文件和work_logs）
- ❌ 没有建立数据恢复SOP（数据被覆盖后如何从备份恢复）
- ❌ 没有定期测试备份的可恢复性

**实际情况：** 8月31日数据被覆盖后，没有自动备份可以恢复。最终是从8月29日的信号文件（碰巧还在）恢复的。如果8月29日的文件也被覆盖了，数据就彻底丢失了。

### 1.5 数据审计日志缺失

**我应该做但没做的：**
- ❌ 没有建立数据审计日志
- ❌ 没有记录每次数据修改的时间、操作人、修改前后的值、修改原因
- ❌ 没有建立"不可变字段修改必须审批"的机制

**实际情况：** 8月31日模拟数据覆盖正确数据后，没有审计日志记录"谁在什么时候把累计盈亏从27030.7改成了-22.43"。无法追溯、无法审计、无法问责。

## 三、我的具体反省

### 反省1：数据质量监控不是"锦上添花"，是数据部的核心职责

我之前觉得数据质量监控是"高级功能"，可以以后再加。

**这次事故证明，数据质量监控是数据部的核心职责，是必需品。** 如果有异常突变检测，8月31日当天就能发现"累计盈亏1000倍变化"，事故就不会扩大。

**正确的做法应该是：**
- 建立数据质量监控体系，每天自动运行
- 监控指标：异常突变、格式一致性、数据来源合法性、数据完整性
- 异常时立即告警，严重异常时自动停止后续操作

### 反省2：数据血缘追踪是快速定位问题的关键

9月修复时，花了10天才找到"数据源被模拟数据覆盖"这个根本原因。

**如果有数据血缘追踪，第一天就能发现问题。** 每个数字都应该有完整的来源链路：这个数字来自哪个work_logs文件？经过了哪个桥接脚本？写入了哪个信号文件？被哪个API读取？在前端哪个位置显示？

**正确的做法应该是：**
- 建立数据血缘追踪日志，记录每次数据转换
- 每个信号文件必须有data_source字段，包含完整的来源信息
- 前端提供"数据来源追溯"功能，用户可以查看任何一个数字的完整来源链路

### 反省3：数据标准是数据质量的基础，必须明确、必须执行

收益率应该用百分比还是小数？累计盈亏应该是"逐日累加"还是"重新计算"？data_source能不能包含"simulated"？

**这些问题在事故发生前都没有明确的答案。** 因为没有数据标准，所以模拟数据可以把收益率写成小数，可以把累计盈亏"重新计算"，可以把data_source标记为"simulated"——这些都不违反任何规定，因为根本没有规定。

**正确的做法应该是：**
- 建立数据标准文档，明确每个字段的定义、格式、单位、取值范围
- 收益率必须用百分比格式（不能用小数）
- 累计盈亏必须是"逐日累加"（不能"重新计算"）
- data_source不能包含"simulated"
- 建立schema校验机制，每次写入信号文件前校验格式是否符合标准
- 不符合标准的数据拒绝写入

### 反省4：数据备份是数据安全的最后一道防线，必须自动化、必须可恢复

8月31日数据被覆盖后，没有自动备份可以恢复。最终是从8月29日的信号文件（碰巧还在）恢复的。

**如果8月29日的文件也被覆盖了，数据就彻底丢失了。** 这是不可接受的。

**正确的做法应该是：**
- 建立数据自动备份机制，每天备份信号文件和work_logs
- 备份保留至少30天
- 建立数据恢复SOP，数据被覆盖后可以快速从备份恢复
- 定期测试备份的可恢复性（每月一次恢复演练）

### 反省5：数据审计是数据治理的基础，必须记录每次修改

8月31日模拟数据覆盖正确数据后，没有审计日志记录"谁在什么时候把累计盈亏从27030.7改成了-22.43"。

**无法追溯、无法审计、无法问责。** 这是数据治理的严重缺失。

**正确的做法应该是：**
- 建立数据审计日志，记录每次数据修改的时间、操作人、修改前后的值、修改原因
- 累计字段（live_total_pnl、live_total_return、live_days）标记为"不可变"
- 修改不可变字段必须经过审批，审批记录写入审计日志
- 审计日志不可篡改（append-only）

## 四、我的改进措施

### 4.1 数据质量监控体系

#### MON-001：异常突变检测（每天）

```
检测规则：
  1. 累计盈亏单日变化超过±50% → 告警
  2. 方向反转（正变负/负变正）→ 告警
  3. 市值接近本金（±1%以内）→ 告警
  4. live_days < 10 → 告警
  5. 收益率格式为小数（绝对值<1且≠0）→ 告警
告警级别：P0，立即通知数据部和运营
严重异常：自动停止后续数据写入操作
```

#### MON-002：数据来源合法性检测（每天）

```
检测规则：
  1. 搜索所有信号文件的data_source字段
  2. 如果包含 "simulated" / "模拟" / "random" → 立即告警并停止
  3. 如果data_source为空 → 告警
  4. 如果data_source不包含"真实" / "real" / "backtest causal" → 告警
告警级别：P0，立即通知数据部
```

#### MON-003：数据格式一致性检测（每天）

```
检测规则：
  1. 收益率字段（live_total_return等）必须为百分比格式（绝对值>1或=0）
  2. 累计盈亏字段（live_total_pnl）必须为数值类型
  3. live_days必须为正整数且>10
  4. 初始本金必须为10000
  5. 当前市值 = 初始本金 + 累计盈亏（允许±0.1%误差）
不符合标准 → 告警，拒绝写入
```

### 4.2 数据血缘追踪体系

```
设计原则：
  1. 每个信号文件必须有data_source字段，包含：
     - 数据来源（work_logs文件路径）
     - 生成时间
     - 生成脚本（bridge_worklog_to_signal.py）
     - 策略版本
  2. 建立"数据血缘日志"，记录每次转换：
     - 源数据位置
     - 目标数据位置
     - 转换时间
     - 转换脚本
     - 转换规则
  3. 前端提供"数据来源追溯"功能
```

### 4.3 数据标准文档

```
必须明确规定：
  1. live_total_pnl：累计盈亏，数值类型，单位元，必须为"逐日累加"
  2. live_total_return：累计收益率，百分比格式（如270.31表示270.31%），禁止小数
  3. live_days：实盘天数，正整数，必须>10
  4. initial_capital：初始本金，必须为10000
  5. total_asset：当前市值，必须=initial_capital + live_total_pnl
  6. data_source：数据来源，必须包含"真实"或"real"或"backtest causal"，禁止包含"simulated"/"模拟"/"random"
  7. 累计字段不可变：live_total_pnl、live_total_return、live_days标记为"不可变"，修改必须经过审批
```

### 4.4 数据备份与恢复机制

```
备份策略：
  1. 每天自动备份信号文件（signals/目录）
  2. 每天自动备份work_logs（/Users/junze/.hermes/work_logs/）
  3. 备份位置：/Users/junze/quant-monitor-local/backups/daily/YYYY-MM-DD/
  4. 备份保留至少30天
  5. 每周做一次全量备份，保留至少90天

恢复SOP：
  1. 确认数据被覆盖的时间点
  2. 找到覆盖前最近的一次备份
  3. 从备份恢复信号文件和work_logs
  4. 验证恢复后的数据正确性（用已知正确值验证）
  5. 重启后端服务
  6. 浏览器实测验证

恢复演练：每月一次，测试备份的可恢复性
```

### 4.5 数据审计日志

```
审计规则：
  1. 每次数据修改必须记录：
     - 修改时间
     - 操作人（AI Agent ID / 用户）
     - 修改的文件和字段
     - 修改前的值
     - 修改后的值
     - 修改原因
  2. 累计字段（live_total_pnl、live_total_return、live_days）修改必须经过审批
  3. 审批流程：修改人提交申请 → 数据部审核 → 用户确认 → 执行修改
  4. 审计日志不可篡改（append-only）
  5. 审计日志保留至少1年
```

## 五、总结

**我犯的最大错误是把数据治理当成了"以后再说"的事情，而不是"第一天就必须建立"的基础。**

**数据质量监控、数据血缘追踪、数据标准、数据备份、数据审计——这些不是"锦上添花"，是数据部的核心职责，是数据安全的基础。**

**这次事故的根本原因之一是数据治理体系缺失：没有监控所以异常没被发现，没有血缘所以问题定位慢，没有标准所以假数据能写入，没有备份所以恢复困难，没有审计所以无法问责。**

**未来我必须记住：数据治理不是成本，是投资。建立数据治理体系的第一天，就能避免未来无数次的数据灾难。**
