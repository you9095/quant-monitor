## 三、我的具体反省

### 反省1："没有消息就是好消息"在运维领域是错误的

我之前的想法是："cron任务在跑，没有报错，应该没问题。"

**这个想法是错误的。** 没有告警不等于系统正常——可能是告警系统坏了，可能是监控覆盖不到，可能是异常被"降级"掩盖了。

**实际情况：**
- 7月6日-8月2日：策略运行100%失败，但桥接阶段继续读已有work_logs，所以"看起来正常"
- 8月3日-8月30日：cron 100%失败，但没有告警，所以"看起来正常"
- 8月31日：模拟模式覆盖了正确数据，但程序"在跑"，所以"看起来正常"

**正确的做法应该是：**
- 主动监控，不是被动等待告警
- 监控"成功率"，不是监控"有没有报错"
- 监控"数据正确性"，不是监控"程序在不在跑"

### 反省2：环境完整性是运营的底线，不是"可以稍后处理"的小问题

pandas是策略运行的基础依赖。没有pandas，策略脚本根本无法启动。

**我把pandas缺失当成了"可以稍后处理"的小问题，但实际上这是运营的底线问题。**

**正确的做法应该是：**
- 基础依赖（pandas、numpy、akshare、flask等）的完整性是运营的第一优先级
- 每天检查基础依赖是否可用：`/usr/local/bin/python3 -c "import pandas, numpy, flask"`
- 发现缺失立即修复，不是"稍后处理"

### 反省3：cron 100%失败必须立即告警，不是"等明天看看"

8月3日之后cron连续28天100%失败（脚本不存在），但没有任何告警。

**这是不可接受的。** cron是自动化系统的核心，cron失败意味着系统停止工作。

**正确的做法应该是：**
- cron任务每次执行后记录状态（成功/失败/失败原因）
- 连续3次失败触发告警
- 告警必须包含：什么任务失败了、为什么失败、怎么处理
- 告警必须通知到具体的人，不是只写在日志里

### 反省4：删除任何东西都必须有记录、有通知、有回滚方案

8月3日删除daily_full_chain.sh等脚本时，没有记录原因，没有通知用户，没有备份。

**这是变更管理的严重缺失。**

**正确的做法应该是：**
- 删除任何文件/脚本前，先备份
- 记录删除原因、删除时间、操作人
- 通知用户和相关角色
- 提供回滚方案（从备份恢复）

## 四、我的改进措施

### 4.1 监控清单（必须执行）

```bash
# 每天9:00执行，检查基础依赖是否可用
/usr/local/bin/python3 -c "
import pandas, numpy, flask, akshare
print('所有基础依赖可用')
print(f'pandas: {pandas.__version__}')
print(f'numpy: {numpy.__version__}')
print(f'flask: {flask.__version__}')
"
# 如果失败，立即告警并修复
```

#### MON-002：cron任务监控（每次执行后）

```
每个cron任务执行后：
  1. 记录执行状态（成功/失败）
  2. 记录失败原因（如果失败）
  3. 连续3次失败 → 触发告警
  4. 告警内容：任务名、失败时间、失败原因、建议处理方式
```

#### MON-003：数据异常突变监控（每天）

```
每天收盘后检查：
  1. 获取最近7天的信号文件
  2. 计算每个策略累计盈亏的日变化率
  3. 如果单日变化超过±50%，或方向反转 → 触发告警
  4. 如果市值接近本金（±1%以内）→ 触发告警
  5. 如果live_days < 10 → 触发告警
```

#### MON-004：模拟模式禁用监控（每天）

```
每天检查：
  1. 搜索代码中的 random.uniform / simulated / 模拟模式
  2. 检查所有信号文件的 data_source 字段
  3. 如果发现模拟模式 → 立即告警并停止
```

### 4.2 环境维护SOP

```
基础依赖维护：
  1. 每天检查pandas、numpy、flask、akshare是否可用
  2. 发现缺失立即安装：/usr/local/bin/python3 -m pip install <package>
  3. 安装后验证：python3 -c "import <package>; print(<package>.__version__)"

Python环境维护：
  1. 确认daily_full_chain.sh用的是哪个Python：which python3
  2. 确认该Python能找到pandas：python3 -c "import pandas"
  3. 如果路径不对，修正脚本中的Python路径
  4. 推荐使用 /usr/local/bin/python3（Homebrew Python 3.14，有pandas 3.0.3）

脚本备份：
  1. 任何关键脚本（daily_full_chain.sh、qixing_daily.sh等）必须有备份
  2. 备份位置：/Users/junze/.hermes/backups/
  3. 修改脚本前先备份
  4. 删除脚本前先备份，并记录原因
```

### 4.3 变更管理SOP

```
任何变更（删除/修改/新增）必须：
  1. 备份当前状态
  2. 记录变更原因、变更时间、操作人
  3. 通知用户和相关角色
  4. 提供回滚方案
  5. 变更后验证系统正常运行

禁止：
  - 未经备份就删除文件
  - 未经通知就修改关键脚本
  - 未经审核就上线新方案（特别是模拟模式这类影响数据真实性的方案）
```

## 五、总结

**我犯的最大错误是"被动等待告警"而不是"主动监控"。没有告警不等于系统正常——可能是监控覆盖不到，可能是异常被掩盖了。**

**pandas缺失28天、cron失败28天、数据被覆盖——这些本应该在第一天就被发现，但因为监控缺失，持续了几十天。**

**未来我必须记住：主动监控、主动发现、主动报告，是运营的核心价值。环境完整性是运营的底线，不是"可以稍后处理"的小问题。**
