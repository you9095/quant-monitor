## 三、我的具体反省

### 反省1：在金融数据系统中，数据真实性比功能完整性更重要

我之前的测试思路是："先测功能能不能跑通，再测数据对不对。"

**这个思路在金融数据系统中是错误的。** 一个能打开但显示错误数据的弹窗，比一个打不开的弹窗危险得多——因为它会误导用户做出错误的决策。

**正确的测试优先级应该是：**
1. **数据真实性测试**（最高优先级）：返回的数字是不是正确的？
2. **数据一致性测试**：前端显示的和后端返回的是不是一致？
3. **数据完整性测试**：所有字段都有值吗？格式对吗？
4. **功能测试**（最低优先级）：弹窗能不能打开？API能不能返回？

### 反省2："降级方案"必须经过最严格的测试

模拟模式是一个"降级方案"——主功能（策略运行）不可用时，用备用方案（随机数）填补。

**在通用软件工程中，"优雅降级"是常见模式。但在金融数据场景下，"降级到假数据"不是优雅降级，是"数据投毒"。**

我没有测试这个降级方案，因为我觉得"这只是个临时方案，很快就会改回来"。

**正确的做法应该是：**
- 任何可能影响数据真实性的方案，都必须经过最严格的测试
- 测试时必须问："这个方案会不会覆盖正确的历史数据？"
- 如果答案是"会"，这个方案就不应该上线

### 反省3：回归测试必须用历史正确数据做基准

每次修改后，我只验证"新功能能不能用"，没有验证"旧数据有没有被改变"。

**这是错误的。** 在金融数据系统中，"不改变正确的历史数据"和"新功能正常工作"同样重要。

**正确的做法应该是：**
- 建立"历史正确数据基准"：追电=27030.7，r32=3080.31，lightning=4712.3，sanhe=1874.57，qixing=-147.55
- 每次修改后，用这个基准做回归测试
- 如果累计盈亏偏离基准超过±5%，测试失败

### 反省4：全链路测试比单点测试更重要

我之前只测前端或只测后端，没有测"数据源→API→前端展示"的完整链路。

**这是错误的。** 数据在链路中可能被多次转换：
- work_logs中的`daily_pnl.cumulative` → 桥接脚本 → 信号文件中的`live_total_pnl` → 后端API → 前端`transformApiData` → 策略卡显示

任何一个环节出错，最终显示的数据都是错的。只测单点无法发现链路中的转换错误。

**正确的做法应该是：**
- 测试完整链路：从work_logs文件开始，经过桥接、API、前端，最终验证策略卡显示的数字
- 每个环节都要验证数据是否正确传递

## 四、我的改进措施

### 4.1 测试用例库（必须执行）

#### TC-001：数据真实性测试（最高优先级）

```
测试目标：验证API返回的累计盈亏是否正确
测试步骤：
  1. 调用 /api/v1/dashboard/portfolio_summary
  2. 提取每个策略的 live_total_pnl
  3. 与历史正确基准对比：
     - 追电 ≈ 27000（允许±5%）
     - r32 ≈ 3000（允许±5%）
     - lightning ≈ 4700（允许±5%）
     - sanhe ≈ 1800（允许±5%）
     - qixing ≈ -150（允许±5%）
通过标准：全部策略在允许范围内
失败处理：立即停止，排查数据源
```

#### TC-002：数据格式测试

```
测试目标：验证收益率格式是否为百分比
测试步骤：
  1. 调用API获取所有策略的 live_total_return
  2. 检查格式：
     - 百分比格式：绝对值 > 1 或 = 0（如270.31表示270.31%）
     - 小数格式（错误）：绝对值 < 1（如2.7031表示270.31%）
通过标准：全部策略都是百分比格式
```

#### TC-003：数据一致性测试（全链路）

```
测试目标：验证前端显示与后端返回一致
测试步骤：
  1. 调用API获取 live_total_pnl
  2. 浏览器打开策略卡，读取显示的总盈亏
  3. 对比两者是否一致
通过标准：前端显示 = API返回
```

#### TC-004：异常突变检测

```
测试目标：检测累计盈亏是否有异常突变
测试步骤：
  1. 获取最近7天的信号文件
  2. 计算每日累计盈亏变化率
  3. 如果单日变化超过±50%，或方向反转，测试失败
通过标准：无异常突变
```

#### TC-005：模拟模式禁用测试

```
测试目标：验证系统中不存在模拟模式
测试步骤：
  1. 搜索所有代码中的 random.uniform / simulated / 模拟模式
  2. 检查所有信号文件的 data_source 字段
通过标准：代码中无模拟模式，信号文件中无 simulated 标记
```

### 4.2 测试SOP

```
每次修改后必须执行：
  1. TC-001 数据真实性测试（必须通过）
  2. TC-002 数据格式测试（必须通过）
  3. TC-003 数据一致性测试（必须通过）
  4. TC-004 异常突变检测（必须通过）
  5. TC-005 模拟模式禁用测试（必须通过）
  6. 浏览器实测9个模块截图（必须通过）

任何一项失败 → 测试不通过 → 不能上线
```

## 五、总结

**我犯的最大错误是用"功能测试"代替了"数据测试"。在金融数据系统中，数据真实性是最高优先级，一个显示错误数据的功能比没有功能更危险。**

**未来我必须记住：测试不通过 = 数据不正确，不是"程序不报错"。**
