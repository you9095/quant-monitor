## 三、真正根因：两套代码并存，改错了那一套

| | 旧版（一直在改） | 新版（gateway 实际在跑） |
|---|---|---|
| 路径 | `~/Library/Python/3.12/lib/python/site-packages/run_agent.py` | `/Users/junze/Apps/hermes-agent-v2026.6.5/` |
| 版本 | v0.14.0 单体（858KB，2026-05-22 普通安装残留） | **v0.21.3 模块化（venv editable 安装）** |
| 谁加载 | 仅命令行直接 `python3` / user site 路径 | **launchd 拉起的 gateway（真正执行 turn 的进程）** |

### 证据链（双重证实）

1. **干净环境 import 测试**：用 `env -i`（模拟 launchd，无 Doubao PYTHONPATH 污染）跑 venv python，verbose 导入显示
   `run_agent → /Users/junze/Apps/hermes-agent-v2026.6.5/run_agent.py`；
   editable finder（`__editable___hermes_agent_0_21_3_finder.py`）MAPPING 正确指向 Apps。
2. **gateway 日志堆栈**：`gateway/run.py` 等栈帧路径全部是 `/Users/junze/Apps/hermes-agent-v2026.6.5/...`，无一处 site-packages。
3. **报错文案来源**：`No reply` 定义在新版 `agent/turn_explainers.py`，退出原因 `rebuilt_restart_limit_exceeded` 在 `agent/turn_iteration_prep.py:478`；旧版单体里 grep 这两个标识符 **0 匹配**。

### 新版代码的真正缺口

v0.21.3 模块化重构后，**旧版的"冷却文件 + 到点自动续试"机制没有移植过来**：

- `agent/fallback_cooldown.py` 只有 primary 的内存级指数退避（`_rate_limited_until`），仅控制何时切回 primary；
- 没有跨会话冷却文件、没有总预算、没有"等待冷却后自动重试"；
- 错误链：`agent/turn_api_error.py settle_unrecovered_error()` → primary transport 恢复 → `_try_activate_fallback()` → 成功则 `_arm_fallback_restart()` 让外层 `restart_count++`；
- `agent/turn_iteration_prep.py`：每次 fallback 切换 restart_count+1，**超过 `max_retries`（默认 3）直接 break turn**；
- break 后 `agent/turn_finalizer.py` 拼出 `No reply … Send continue`，gateway 层无自动重新排队。

即：所有 provider 因同一出口 IP 被限流集体失败时，新版遍历完 3 次 restart 上限就放弃 turn，等用户续命。

## 四、修复：两条失败路径都接入"自动冷却恢复"

改在 **Apps 目录 v0.21.3**（gateway 实际代码），3 个文件：

### 新增 `agent/turn_iteration_prep.py::_attempt_fallback_chain_cooldown()`

链耗尽时不再直接 break：
1. 每 turn 计数 `agent._turn_fallback_cooldown_retries`，上限 `HERMES_FALLBACK_AUTO_RECOVER_MAX`（默认 1）；
2. `_emit_status` + 中文提示"所有备用模型均失败，自动冷却 N 秒后重试，无需手动继续"；
3. 用 `interruptible_backoff_sleep` 分片等待 `HERMES_FALLBACK_COOLDOWN_SECONDS`（默认 45s），200ms 一切片可随时中断；
4. 等待中被中断 → 返回中断结果（不重试）；带 redirect 的中断 → 交 redirect 分支；
5. 冷却完：清 `_rate_limited_until/_rate_limit_backoff_count`，`_restore_primary_runtime()`（失败则兜底手动重置 `_fallback_index/_fallback_activated`），重置 restart/retry 计数，**自动 continue**。

### 路径 A：`turn_iteration_prep.py` rebuilt_restart_limit_exceeded

原来 `restart_count > max_retries` 直接 break；现在先尝试冷却恢复，成功则清计数器 continue，次数用尽才 break。

### 路径 B：`turn_api_error.py` max_retries_exhausted

原来 retry_count 超限且无 fallback 可切（`_try_activate_fallback()` 返回 False）直接 `max_retries_exhausted_result()` 终态返回；现在同样先冷却恢复，成功则 `retry_count=0` continue。

### `agent/conversation_loop.py`

每 turn 初始化处 `agent._turn_fallback_cooldown_retries = 0`，保证冷却次数按 turn 计。

### 调优项（不改默认也能工作）

| 环境变量 | 默认 | 含义 |
|---|---|---|
| `HERMES_FALLBACK_COOLDOWN_SECONDS` | 45 | 全链失败后自动等待秒数 |
| `HERMES_FALLBACK_AUTO_RECOVER_MAX` | 1 | 每 turn 最多自动冷却恢复次数（防上游真挂时空转） |

## 六、铁律（本次教训）

1. **改 Hermes 代码前，先确认 gateway 实际加载哪个文件**：本机是 git+editable 安装在 `/Users/junze/Apps/hermes-agent-v2026.6.5/`，**不是** `~/Library/Python/3.12/.../site-packages`。验证方法 = `env -i` 干净环境 verbose import + gateway 日志栈路径，**不要**只跑检查脚本就下结论。
2. **"测试全过"要看测的是不是活代码**：check_429_guard.py 测的是 site-packages 旧文件，给出的全绿是假象。
3. **报错文案即导航**：`No reply` / `rebuilt_restart_limit_exceeded` 这类字符串直接 grep 源码，比凭旧锚点猜位置快得多。
4. **分层防护不能丢**：模块化重构时，旧版的冷却续试机制必须显式移植，否则"看似有重试/fallback"实则链一耗尽就放弃 turn。
