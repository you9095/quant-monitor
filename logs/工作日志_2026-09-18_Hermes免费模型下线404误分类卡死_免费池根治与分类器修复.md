# 2026-09-18 Hermes No-reply 卡死根治：免费模型下线 404 误分类 + 免费池/遍历预算配置根治

> 触发：9-17 刚做完"全链耗尽自动冷却恢复"并卸载旧版残留后，9-18 晚用户再次遇到
> `⚠️ No reply: every provider in the fallback chain kept failing over … Send continue`，
> 仍需手动发"继续"。用户质疑：OpenRouter 免费模型 40+，不可能一个能用的都没有；
> 并重申最高铁律——**默认只用免费模型，收费模型仅在当轮主动明确要求时可用**；
> 核心诉求不变：**No reply 后必须全自动恢复，绝不卡住、不要手动 continue（含 cron 无人值守任务）**。
>
> 结论：9-17 的冷却机制确实在工作（当天触发 27 次），但它针对"临时限流"设计；
> 本次是"主模型永久下线 + fallback 链太短 + 单 turn 遍历预算=1 + 404 措辞误分类"四重叠加，
> 冷却后必然二次失败。本次从**配置层 + 错误分类代码层**两处根治，纯免费，已端到端验证通过。

## 一、现象与定性

- agent.log 22:29–23:01 反复出现 `Fallback chain exhausted; entering auto cooldown 45s (recovery 1/1)`，
  每次"冷却 45s → 重试 → 几秒内再次全挂 → 第 2 次耗尽（每 turn 上限 1 次）→ 停 turn 弹 No reply"。
- 无人值守 cron `takeover-redispatch-worker` 因此 `RuntimeError: No reply` 直接失败。
- 冷却函数末尾 `_restore_primary_runtime()` 会把链重置回主模型——而主模型已永久 404，
  所以"自动恢复"必然二次失败。**冷却针对临时限流的假设，在"主模型永久下线"下不成立。**

## 二、四层根因（均有日志/实测铁证）

1. **主模型 slug 永久 404 下线**：`minimax/minimax-m3:free` 被 OpenRouter 返回
   `HTTP 404 "This model is unavailable for free. The paid version is available now - use this slug instead: minimax/minimax-m3"`。
   `curl` 经代理实测 **1.25s 秒回 404**（不是网络问题）。
2. **fallback 链太短且厂商集中**：config 静态写死 3 个 openrouter 免费模型（nvidia/cohere 晚高峰最易过载）+ 1 个 zai；
   当时 OpenRouter 上十余个健康免费模型（deepseek-v4-flash、qwen3.8、nex、ling、liquid 等）从未被尝试。
3. **`agent.api_max_retries: 1` 是隐藏硬瓶颈**：每次 fallback 切换都 arm 一次 `restart_with_rebuilt_messages`，
   外层 `restart_count += 1`，上限即 `max_retries`（代码：先 `restart_count += 1` 再判 `restart_count > max_retries`）。
   =1 时一个 turn 主模型失败后**最多再试 1 个 fallback** 就撞 `rebuilt_restart_limit_exceeded`，链配多长都遍历不到。
4. **【代码根因·最关键】下线 404 的措辞被错误分类**：`agent/error_classifier.py` 的 404 规则
   （`_404_RULES`：BILLING → POLICY → MODEL_NOT_FOUND）都不含 "unavailable for free / paid version is available /
   use this slug instead" 这组 OpenRouter 特有措辞，末尾落到 `_V_UNKNOWN`。
   实测真实分类结果：`reason=unknown, retryable=True, should_fallback=False`
   ——**当作可重试未知错误，在同一个死模型上反复重试 + backoff sleep，绝不切换**。
   故障注入实测：该路径进程 99% CPU 时间在 `time_sleep`，挂 4 分钟以上不前进（这正是用户感知的"卡住"）。

## 三、为什么"设了那么多机制"还是卡（机制碎片化，各管一段）

| 机制 | 谁维护 | 现状 |
|---|---|---|
| A. config.yaml `fallback_providers` → `agent._fallback_chain` | 内置 agent_init/try_activate_fallback | **v0.21 turn 内实时 fallback 唯一读取来源**；grep 证实 Apps 代码 0 处读 state chain.json |
| B. hook `or-429-immediate-switch.py` 写 `state/openrouter-fallback-chain.json` | 旧防御体系（含"收费模型严禁入池"硬闸门） | **新版 turn 代码不读该文件**，不参与实时遍历（动态拉全量免费模型能力被架空） |
| C. `auto_model_router.py`（关键词切 deepseek/minimax **官方付费**渠道） | 用户自配，"主动要求除外" | 仅关键词触发，平时不动；保留 |
| D. 9-17 全链耗尽自动冷却（45s/turn 1 次） | turn_iteration_prep/turn_api_error | 对临时限流有效；对永久 404 主模型，冷却后 restore 回死模型必再失败 |
| E. openrouter-watchdog | 独立看门狗 | 状态陈旧（main 仍指 google_gemma，不在新链），与 turn 不连通 |

教训：**机制数量不等于可靠性**；多套并行、互不连通、有的要重启/不被读取，给人"已经修过"的错觉。

### 代码层 `agent/error_classifier.py`（备份 `error_classifier.py.bak.20260918_free404`）

## 九、9-19 P1 加固（在 9-18 根治之上堵死极端情况）

用户确认继续做三个 P1，全部落地并验证：

- **P1-B 永久故障模型不切回（核心）**：新增 `fallback_cooldown._mark_permanent_model_failure / _is_permanently_unavailable`
  （per-session set，重启重新探测）；三处挂载：① `chat_completion_helpers._should_skip_fallback_candidate` 跳过被标记 slug；
  ② `agent_runtime_helpers.restore_primary_runtime` 对被标记主模型 `return False`（不切回，留在健康 fallback）；
  ③ `turn_api_error` 在 `classify==model_not_found` 时自动标记。彻底断掉 9-18 的"死主模型→fallback→冷却→restore 回死主模型→再失败"循环。

- **P1-C cron 无人值守双保险**：`~/.hermes/scripts/llm_fallback_cron.sh` 的错误识别正则加入
  `No reply / every provider / fallback chain / Send continue`，且重跑前 `sleep 45s`（等 Hermes 冷却跑完）。
  此前 No reply 不被识别，cron 直接失败。
